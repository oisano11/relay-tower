# 修复计划与验收

范围：修复项目分析中的 14 类确定性问题；不连接生产数据库、不执行真实切线或发送 Telegram 消息。

1. 部署与认证：镜像包含代码；回环判断使用 socket；Cookie 容错；Telegram 仅授权个人；请求统一兜底。
2. 网关：独立代理模块；停用通道不得选中；保留查询参数；替换上游凭证；首字超时、断流取消与真实指标。
3. 数据一致性：数据库错误必须上抛；SQL 经 stdin 传递；切线与改价先提交远端事务再更新内存；充值检查目标存在。
4. 巡检与审批：修复故障分组引用；统一模型 URL；识别冷备；审批仅修改来源通道并同步数据库。
5. 调度：人工锁定独立于优先级；按当前组售价判断利润；使用真实连续失败与首字阈值；共享账号不执行跨组停调。
6. 验收：隔离回归测试、原巡检测试、语法检查、CI 启动检查；更新文档中的能力边界。

各批次以测试为准。跨组调度支持一个渠道属于多个分组：专属独立渠道在单主独占模式下进入冷备 (`schedulable=false, priority=10`)；跨组共享渠道保留全局调度开关 (`schedulable=true`) 仅调低当前组内优先级 (`priority=10`)，杜绝跨组误杀，不修改上游数据库结构。异步数据库迁移和前端整体拆分列为后续架构工作，避免与本次正确性修复混杂。

## 自动调配逻辑修复（2026-09-24）

目标：让塔台对 Sub2API 已接入渠道的“故障切走 → 充值/恢复 → 自动切回”闭环在真实环境可用。

1. **欠费标记不再永久卡死**：欠费证据按“最新可信观测”判定。查不到余额（unknown）的账号，由一次真实 1 token 生成成功解除欠费；不限额账号在额度报错窗口过去且余额刷新后解除。修正 baseUrl 以 `/v1` 结尾时余额请求变成 `/v1/v1/usage` 的问题。
2. **OAuth / Setup-Token 账号不再被误判离线**：无 API Key 的账号标记 `passiveHealth`，不做 HTTP 探活，只按真实请求统计判断；Anthropic 平台探活补 `anthropic-version` 头。
3. **切回前必须真实生成成功**：请求级故障（失败率、首字超时、连续失败）后，仅 `/v1/models` 可达不再算恢复；调度器对需要证明的账号每 5 分钟（`generationProbeIntervalMs`）发一次 1 token 请求，流内首帧错误也判失败。`requireGenerationProbe: false` 可关闭。
4. **无备选时不再整组停服**：只关停确认欠费或人工停用的独占账号；失败率高、首字慢、探活失败、倍率高于售价的主调保持服务并告警。
5. **关键字例外渠道不被自动化触碰**：当主调是例外渠道时整组保持人工控制；切线与耗尽处理都不会关停例外渠道。人工停用（`autoSwitchDisabled`）仍可被迁出。
6. **主调判定口径统一为 `accounts.priority`**：已核对 Sub2API 源码，调度器最终按账号全局优先级排序，`account_groups.priority` 只影响查询顺序，不能实现分组级主备。
7. **过期决策闸门生效**：路由版本在评估前取值。
8. **额度识别收紧**：Sub2API 统计侧不再用宽泛的 `quota|balance`，429 限流不再算欠费；新增 Anthropic “credit balance is too low”。
9. **候选排序可选**：`candidateOrder: "cost"`（默认，成本优先）或 `"role"`（按主调/副调/备选/备用优先级）。
10. **Redis 刷新改为 SCAN**：不再用阻塞的 `KEYS`。

## 轮换补强与上线验证（2026-09-24）

- **不提供 `/v1/models` 的上游可以当备选了**：探活返回 404/405 时改用真实生成探测（默认每 5 分钟 1 token）。最近一次生成成功才算在线；失败或过期记为“未知”（不当备选，但也不累计探活失败，真实流量故障仍由请求统计判断）。上游巡检不会覆盖这类账号的状态。
- **探测模型自动回退**：候选顺序为上次成功的模型 → 模型映射 → 分组所需模型 → 上游发现的模型 → 平台默认模型，最多试 4 个。只有“模型不存在 / 该分组无此模型”才换下一个；欠费、服务器错误不会浪费额外请求。全部不存在时状态为 `unknown_model`，提示去 Sub2API 配置模型映射。
- **切号预演（只读）**：控制台【⚙️ 系统管理 → 🧭 切号预演】/ `GET /api/auto-switch/preview`，与真实切号共用同一套输入和决策逻辑，逐组列出当前主调、将切到谁、每个账号为什么能或不能当备选。不写数据库、不改运行时状态。

- **自动切号面板**：顶部显示各分组的保护情况（有备用 / 没有可用备用及原因 / 人工管理 / 当前出故障且无备用）；说明改为与实际逻辑一致的大白话（原文“单主独占”“低价回切”与线上配置不符）。保存时只提交面板上的设置，不再把首字超时、欠费确认次数等隐藏项覆盖成写死的值。
- **请求少的分组也能切走**：原规则只看最近 5 分钟，请求少时“连续失败 30 次 / 样本 50 次”永远凑不够，上游“能连上但生成失败”时会一直停在坏账号上。现在窗口内请求数不足连续失败门槛、且最近 3 次真实请求连续失败时，塔台 2 分钟内补一次 1 token 真实生成探测；探测也失败才判为请求故障并切到备用。请求多的账号仍只按原门槛判断；探测成功或只是模型不存在都不算故障。

- **分组自动切号设置跟随全站**：打开分组设置时显示全站当前值（以前显示写死的旧数字，低价/混池组还会填入 80%/样本 100/连续 50 次），保存时只记下与全站不同的项，其余继续跟随全站；新增「全部跟随全站」。修复「便宜账号恢复后自动换过去」开关读写的字段名不一致（显示永远“已开启”、保存永远“关闭”），补上「一键填入」要用的 10 次选项（以前会被悄悄存成默认值）。

上线建议：只有 1 个账号的分组出故障时无处可切，需要补充同类模型、进价不高于售价的备用账号；请求量少的站点可以调低全站「样本量」和「连续连不上」次数（需在控制台保存）。测试 159/159。

## 接入上游新 Key（2026-09-25）

在上游 Sub2API 站点新建的 Key，自动出现在控制台【⚙️ 系统管理 → 🆕 接入上游新 Key】，选好本站分组后一键在本站 Sub2API 建账号。接口：`GET /api/upstream/keys`（`?refresh=true` 立即重读）、`POST /api/upstream/keys/connect`、`POST /api/upstream/keys/dismiss`。逻辑在 `upstream-keys.js`。

- **发现**：每 10 分钟同步上游余额后，用「上游供应商后台」里的登录信息读取各家上游的 `/api/v1/keys` 和 `/api/v1/groups/rates`（接口按 Sub2API 开源代码核对）。本站没有账号在用的 Key 算待接入，进价取上游专属倍率，没有则取分组倍率。每个新 Key 只提醒一次（告警盒 + Telegram）。完整 Key 只在服务端使用，页面只显示末 4 位。
- **接入**：整行复制同一家上游、同平台的现有账号（与拆分共享账号相同的写法），只换 Key、名称、进价和分组；清掉报错、限流、到期等旧状态和旧的倍率探测数据。参照账号属于同一个上游分组时保留模型映射，否则不限模型。空分组直接当主调；已有账号时先当备用（单主独占模式下不接流量）。
- **拦截**：分组平台不对、进价不低于售价、这家上游还没有同平台账号可参照、Key 已接入过，都会拒绝并说明原因；数据库里还有同样的守卫，任何一步失败都不写入。
- **删除**：只是不再提示这个 Key（记录在 `data/upstream_key_state.json`），可以恢复，不动上游。
- **暂不支持**：New-API 系统的上游（读 Key 的接口不同）；只存了令牌、没存账号密码的上游，令牌过期后需要在「上游供应商后台」重新填写。

验收：`npm test` 170/170（新增 `scripts/test-upstream-keys.js`）；接入语句在按 Sub2API 表结构手写的本地 PostgreSQL 18 上实测：建号、备用与主调、保留或去掉模型映射、重复 Key / 倒贴 / 分组不存在的拦截均符合预期。接口字段已在真实 Sub2API 上游只读核对。

## 删除业务分组（2026-09-25）

以前删除分组又慢又常被拦。只要分组里有在接单、且只属于这个分组的账号，删除就会被「删除后没有可核验售价分组」拦下。拆分共享账号以后，几乎每个分组都是这种情况。删除时还要同步执行七到九次 `docker exec`（写库、四次 Redis 缓存清理、签名、全量重读账号），塔台会整个卡住一两秒，页面上没有任何提示。旧逻辑也不检查客户 Key，而 Sub2API 会直接拒绝所属分组已删除的 Key（403「API Key 所属分组已删除」）。

- **先检查**：新接口 `GET /api/groups/:id/delete-preview` 列出会一起停用的账号（在接单且只在这个分组里）和只会移出分组的账号。它还会只读查询这些绑定：客户 Key、订阅，以及把这个分组设为备用分组（`fallback_group_id` / `fallback_group_id_on_invalid_request`）的其他分组。
  - **客户 Key**：和 Sub2API 自带的删除一样，确认后照样能删。确认框写明有几个 Key、几位客户、最近 7 天有没有人用，并列出每个 Key 属于哪位客户（邮箱，没有邮箱时用用户名）、最后使用时间，最多列 20 个。不读取 Key 本身。
  - **订阅和备用分组**：仍然不让删，弹窗说明要先在 Sub2API 后台做什么。
- **一次删完**：`DELETE /api/groups/:id` 要带上确认过的 `stopAccountIds` 和 `confirmKeyCount`。停用名单要和服务端重新算出的完全一致，否则提示刷新后重试。整个删除在同一个事务里按这个顺序执行：
  1. 锁住分组，再查一遍：客户 Key 不能比确认时多（旧页面不带数量，按 0 处理），不能有订阅，不能被当成备用分组。
  2. 停用名单里的账号。数据库里会先确认它们没有加入别的分组。
  3. 过原有的两道守卫：不留下没有分组的在用账号，剩余分组不倒贴。
  4. 按 Sub2API 自带删除的做法清理 `user_allowed_groups` 和 `account_groups`。`composite_model_routes` 有 `deleted_at` 字段时一并软删除。
  5. 软删除分组。Sub2API 从迁移 184 起在 `groups` 表上有触发器 `trg_groups_auth_cache_invalidation`，它会让这个分组下客户 Key 的登录缓存失效，所以这些 Key 很快会被拒绝，和在 Sub2API 后台删除一样。更早的版本要等登录缓存过期，默认最多 5 分钟。
- **不再卡住**：请求只等这一次写库。调度缓存清理和账号重读交给后台子进程（`requestBackgroundSchedulerInvalidation`、`refreshSub2APISignatureAfterDirectMutation(…, true)`）。
- **不再误拦**：分组自己的售价是 0 或没填也能删。已停用的账号只更新本地缓存，不会再因为它所在的其他分组售价核对不上而拦下删除。
- **提示看得懂**：数据库拒绝时，错误会翻译成中文说明，并注明「这次没有删除」。删除按钮会显示「检查中…」和「正在删除…」，防止重复点击。分组名不再拼进页面的 onclick。

验收：删除分组相关用例共 8 个，全部通过（全量 `npm test` 180/180）。删除语句在按 Sub2API 表结构手写的本地 PostgreSQL 18 上实测了 12 种情况，结果都符合预期，被拒绝时数据不变：
- 确认停用后删除
- 客户 Key 比确认时多（包括旧页面不带数量）
- 确认过客户 Key 数量后删除
- 查出每个 Key 的客户：有邮箱、只有用户名、用户已不存在
- 在用账号未确认停用
- 停用名单里的账号已加入别的分组
- 共享账号只移出
- 被设为备用分组
- 有订阅
- 售价为 0
- 剩余分组倒贴
- 缺少可选字段的旧表结构

## 部署脚本中文环境修复（2026-09-25）

macOS 自带的 bash 3.2 在中文（UTF-8）环境下，会把紧跟在 `$变量` 后面的中文当成变量名的一部分，脚本在 `set -u` 下报「unbound variable」后停止。`deploy/deploy.sh` 里紧跟中文的变量都改成了 `${变量}` 写法。

## 上游改价跟价与改价提醒（2026-09-25）

用户反馈：上游改价后，塔台的进价没有变，也没有收到改价提醒。查到两个原因。

- **提醒丢失**：从 d322e1d（09-20）起，`handleRatioChange` 在写倍率历史时引用了不存在的变量 `direction`，每次检测到倍率变化都会抛出 `ReferenceError`。后台同步在合并完新倍率之后才调用它，所以抛错后本轮同步被记为失败：`channels.json` 没有写入，没有广播，也没有 `RATIO_ALERT` 和 Telegram 推送。5 秒后的下一轮同步把新数字补上，但提醒和倍率历史已经丢了。直接同步（启动、手动刷新）遇到倍率变化时，整次同步都会返回失败。已改为 `direction: alert.direction`。之前的测试都把 `handleRatioChange` 换成了空函数，所以没有测到这个问题。新增 2 个用例直接运行真实的处理函数，改动前会报同样的 `ReferenceError`。
- **不跟价**：6f3a8b8（09-21）为了不让过期的上游数据盖过手填的倍率，把进价规则改成：没开 `upstream_billing_rate_sync_enabled` 且 `rate_multiplier ≠ 1` 时一律用 `rate_multiplier`。但 Sub2API 的上游计费探测（`/v1/sub2api/billing`，默认 30 分钟一次）对没开同步的账号也照常更新 `upstream_billing_probe`，只是不改写 `rate_multiplier`。所以对这类账号，塔台就看不到上游改价了。
- **新规则**（`syncRealSub2APIAccounts` 的查询、`executeControlPlaneSafetyPlan` 的 `currentCostSql`、`remoteEffectiveCostSql` 三处保持一致）：
  1. 开了自动同步：用上游价。
  2. 没开，但 `upstream_billing_probe.status = 'ok'` 且 `fresh_until` 还没到（Sub2API 写入的是收到时间加两个探测周期）：仍用上游价。
  3. 否则用 `rate_multiplier`。
  4. 它还是默认值 1 时，退回上游最后一次报的价。

  `fresh_until` 要先用正则确认是时间格式，再在 `CASE` 里转成 `timestamptz`。PostgreSQL 不保证 `AND` 两边的求值顺序，这样写可以保证坏数据不会让整条查询报错。
- **验收**：`npm test` 179/179。把三处的真实 SQL 放到按 Sub2API 表结构手写的本地 PostgreSQL 18 上，跑了 12 种探测状态：开或没开同步、上游价有效或已过期、查询失败、不支持、探测已关闭、时间带 9 位小数、不带小数、带 `+08:00` 时区、格式错误、缺少 `fresh_until`、倍率为默认 1。三处算出的进价都一致，安全动作 SQL 复核时也没有判为过期。上线前在生产库只读核对过：规则改变后进价会变的账号，新进价都不高于所在分组的售价，不会触发自动停用。
