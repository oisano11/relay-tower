# 修复计划与验收

范围：修复项目分析中的 14 类确定性问题；不连接生产数据库、不执行真实切线或发送 Telegram 消息。

1. 部署与认证：镜像包含代码；回环判断使用 socket；Cookie 容错；Telegram 仅授权个人；请求统一兜底。
2. 网关：独立代理模块；停用通道不得选中；保留查询参数；替换上游凭证；首字超时、断流取消与真实指标。
3. 数据一致性：数据库错误必须上抛；SQL 经 stdin 传递；切线与改价先提交远端事务再更新内存；充值检查目标存在。
4. 巡检与审批：修复故障分组引用；统一模型 URL；识别冷备；审批仅修改来源通道并同步数据库。
5. 调度：人工锁定独立于优先级；按当前组售价判断利润；使用真实连续失败与首字阈值；共享账号不执行跨组停调。
6. 验收：隔离回归测试、原巡检测试、语法检查、CI 启动检查；更新文档中的能力边界。

各批次以测试为准。跨组调度支持一个渠道属于多个分组：专属独立渠道在单主独占模式下进入冷备 (`schedulable=false, priority=10`)；跨组共享渠道保留全局调度开关 (`schedulable=true`) 仅调低当前组内优先级 (`priority=10`)，杜绝跨组误杀，不修改上游数据库结构。异步数据库迁移和前端整体拆分列为后续架构工作，避免与本次正确性修复混杂。

## 自动切号第二阶段（当前实施）

目标：已接入的同组账号自动容灾、充值后自动恢复；人主要负责充值。上游新增分组发现另行实施。

1. 将故障判断抽为独立策略：连续探活失败或足够的实际请求失败确认故障；新鲜可信欠费记录立即隔离。查余额失败与陈旧观测不能伪装成新欠费。
2. 统一执行切换：同组、有资格、健康、满足明确模型配置且成本不超过售价的候选按成本选择。故障切换不受回切冷却阻挡，不再要求逐次人工审批，也不修改售价。
3. 恢复防抖：恢复后需连续健康观测和稳定等待；回切便宜号另需满足价差与冷却。已确认欠费需重新查到正余额，不能仅凭模型列表能打开判为充值成功。
4. 单独保存人工停用标记，冷备用不等于人工停用；遵守全局及分组开关。探活只记录状态，不独立永久关闭分组。
5. SUB2 原生优先级统一为数字越小越优先；移除启动时强制定性的隐式写入。部署前不修改线上账号。
6. 验收覆盖瞬断、欠费、恢复、防反复切换、全部不可用、人工停用、分组/模型范围和数据库失败。

前端入口已收拢：自动切号只保留统一策略设置和每组策略覆盖；故障切换不再弹人工批准窗口，也不再提供重复的按成本定性按钮。人工停用仍是明确的候选池排除操作；上游巡检中的新模型/同价渠道待办仍保留人工确认，因为它们可能影响对外可用范围。

## 自动调配逻辑修复（2026-09-24）

目标：让塔台对 Sub2API 已接入渠道的“故障切走 → 充值/恢复 → 自动切回”闭环在真实环境可用。

1. **欠费标记不再永久卡死**：欠费证据按“最新可信观测”判定。查不到余额（unknown）的账号，由一次真实 1 token 生成成功解除欠费；不限额账号在额度报错窗口过去且余额刷新后解除。修正 baseUrl 以 `/v1` 结尾时余额请求变成 `/v1/v1/usage` 的问题。
2. **OAuth / Setup-Token 账号不再被误判离线**：无 API Key 的账号标记 `passiveHealth`，不做 HTTP 探活，只按真实请求统计判断；Anthropic 平台探活补 `anthropic-version` 头。
3. **切回前必须真实生成成功**：请求级故障（失败率、首字超时、连续失败）后，仅 `/v1/models` 可达不再算恢复；调度器对需要证明的账号每 5 分钟（`generationProbeIntervalMs`）发一次 1 token 请求，流内首帧错误也判失败。`requireGenerationProbe: false` 可关闭。
4. **无备选时不再整组停服**：只关停确认欠费或人工停用的独占账号；失败率高、首字慢、探活失败、倍率高于售价的主调保持服务并告警。
5. **关键字例外渠道不被自动化触碰**：当主调是例外渠道时整组保持人工控制；切线与耗尽处理都不会关停例外渠道。人工停用（`autoSwitchDisabled`）仍可被迁出。
6. **主调判定口径统一为 `accounts.priority`**：已核对 Sub2API 源码，调度器最终按账号全局优先级排序，`account_groups.priority` 只影响查询顺序，不能实现分组级主备。
7. **过期决策闸门生效**：路由版本在评估前取值。
8. **额度识别收紧**：Sub2API 统计侧不再用宽泛的 `quota|balance`，429 限流不再算欠费；新增 Anthropic “credit balance is too low”。
9. **候选排序可选**：`candidateOrder: "cost"`（默认，成本优先）或 `"role"`（按主调/副调/备选/备用优先级）。（2026-09-27 起取消这个选项，固定按角色：副调 → 备选，备用不当候选。）
10. **Redis 刷新改为 SCAN**：不再用阻塞的 `KEYS`。

## 轮换补强与上线验证（2026-09-24）

- **不提供 `/v1/models` 的上游可以当备选了**：探活返回 404/405 时改用真实生成探测（默认每 5 分钟 1 token）。最近一次生成成功才算在线；失败或过期记为“未知”（不当备选，但也不累计探活失败，真实流量故障仍由请求统计判断）。上游巡检不会覆盖这类账号的状态。
- **探测模型自动回退**：候选顺序为上次成功的模型 → 模型映射 → 分组所需模型 → 上游发现的模型 → 平台默认模型，最多试 4 个。只有“模型不存在 / 该分组无此模型”才换下一个；欠费、服务器错误不会浪费额外请求。全部不存在时状态为 `unknown_model`，提示去 Sub2API 配置模型映射。
- **切号预演（只读）**：控制台【⚙️ 系统管理 → 🧭 切号预演】/ `GET /api/auto-switch/preview`，与真实切号共用同一套输入和决策逻辑，逐组列出当前主调、将切到谁、每个账号为什么能或不能当备选。不写数据库、不改运行时状态。

### 上线验证步骤

1. 部署后打开【🧭 切号预演】，逐组核对：当前主调是否正确；每组至少有一个“可做备选”；“不可用”账号的原因是否符合实际。共享账号先用【🧩 拆分共享账号】拆开。

- **请求少的分组也能切走**：原规则只看最近 5 分钟，请求少时“连续失败 30 次 / 样本 50 次”永远凑不够，上游“能连上但生成失败”时会一直停在坏账号上。现在窗口内请求数不足连续失败门槛、且最近 3 次真实请求连续失败时，塔台 2 分钟内补一次 1 token 真实生成探测；探测也失败才判为请求故障并切到备用。请求多的账号仍只按原门槛判断；探测成功或只是模型不存在都不算故障。

- **分组自动切号设置跟随全站**：打开分组设置时显示全站当前值（以前显示写死的旧数字，低价/混池组还会填入 80%/样本 100/连续 50 次），保存时只记下与全站不同的项，其余继续跟随全站；新增「全部跟随全站」。修复「便宜账号恢复后自动换过去」开关读写的字段名不一致（显示永远“已开启”、保存永远“关闭”），补上「一键填入」要用的 10 次选项（以前会被悄悄存成默认值）。

上线建议：只有 1 个账号的分组出故障时无处可切，需要补充同类模型、进价不高于售价的备用账号；请求量少的站点可以调低全站「样本量」和「连续连不上」次数（需在控制台保存）。测试 159/159。

在上游 Sub2API 站点新建的 Key，自动出现在控制台【⚙️ 系统管理 → 🆕 接入上游新 Key】，选好本站分组后一键在本站 Sub2API 建账号。接口：`GET /api/upstream/keys`（`?refresh=true` 立即重读）、`POST /api/upstream/keys/connect`、`POST /api/upstream/keys/dismiss`。逻辑在 `upstream-keys.js`。

## 删除业务分组（2026-09-25）

以前删除分组又慢又常被拦。只要分组里有在接单、且只属于这个分组的账号，删除就会被「删除后没有可核验售价分组」拦下。拆分共享账号以后，几乎每个分组都是这种情况。删除时还要同步执行七到九次 `docker exec`（写库、四次 Redis 缓存清理、签名、全量重读账号），塔台会整个卡住一两秒，页面上没有任何提示。旧逻辑也不检查客户 Key，而 Sub2API 会直接拒绝所属分组已删除的 Key（403「API Key 所属分组已删除」）。

- **先检查**：新接口 `GET /api/groups/:id/delete-preview` 列出会一起停用的账号（在接单且只在这个分组里）和只会移出分组的账号。它还会只读查询这些绑定：客户 Key、订阅，以及把这个分组设为备用分组（`fallback_group_id` / `fallback_group_id_on_invalid_request`）的其他分组。
  - **客户 Key**：和 Sub2API 自带的删除一样，确认后照样能删。确认框写明有几个 Key、几位客户、最近 7 天有没有人用，并列出每个 Key 属于哪位客户（邮箱，没有邮箱时用用户名）、最后使用时间，最多列 20 个。不读取 Key 本身。
  - **订阅和备用分组**：仍然不让删，弹窗说明要先在 Sub2API 后台做什么。
- **一次删完**：`DELETE /api/groups/:id` 要带上确认过的 `stopAccountIds` 和 `confirmKeyCount`。停用名单要和服务端重新算出的完全一致，否则提示刷新后重试。整个删除在同一个事务里按这个顺序执行：
  1. 锁住分组，再查一遍：客户 Key 不能比确认时多（旧页面不带数量，按 0 处理），不能有订阅，不能被当成备用分组。
  2. 停用名单里的账号。数据库里会先确认它们没有加入别的分组。
  3. 过原有的两道守卫：不留下没有分组的在用账号，剩余分组不倒贴。
  4. 按 Sub2API 自带删除的做法清理 `user_allowed_groups` 和 `account_groups`。`composite_model_routes` 有 `deleted_at` 字段时一并软删除。
  5. 软删除分组。Sub2API 从迁移 184 起在 `groups` 表上有触发器 `trg_groups_auth_cache_invalidation`，它会让这个分组下客户 Key 的登录缓存失效，所以这些 Key 很快会被拒绝，和在 Sub2API 后台删除一样。更早的版本要等登录缓存过期，默认最多 5 分钟。
- **不再卡住**：请求只等这一次写库。调度缓存清理和账号重读交给后台子进程（`requestBackgroundSchedulerInvalidation`、`refreshSub2APISignatureAfterDirectMutation(…, true)`）。
- **不再误拦**：分组自己的售价是 0 或没填也能删。已停用的账号只更新本地缓存，不会再因为它所在的其他分组售价核对不上而拦下删除。
- **提示看得懂**：数据库拒绝时，错误会翻译成中文说明，并注明「这次没有删除」。删除按钮会显示「检查中…」和「正在删除…」，防止重复点击。分组名不再拼进页面的 onclick。

验收：删除分组相关用例共 8 个，全部通过（全量 `npm test` 180/180）。删除语句在按 Sub2API 表结构手写的本地 PostgreSQL 18 上实测了 12 种情况，结果都符合预期，被拒绝时数据不变：
- 确认停用后删除
- 客户 Key 比确认时多（包括旧页面不带数量）
- 确认过客户 Key 数量后删除
- 查出每个 Key 的客户：有邮箱、只有用户名、用户已不存在
- 在用账号未确认停用
- 停用名单里的账号已加入别的分组
- 共享账号只移出
- 被设为备用分组
- 有订阅
- 售价为 0
- 剩余分组倒贴
- 缺少可选字段的旧表结构

## 上游改价跟价与改价提醒（2026-09-25）

用户反馈：上游改价后，塔台的进价没有变，也没有收到改价提醒。查到两个原因。

- **提醒丢失**：从 d322e1d（09-20）起，`handleRatioChange` 在写倍率历史时引用了不存在的变量 `direction`，每次检测到倍率变化都会抛出 `ReferenceError`。后台同步在合并完新倍率之后才调用它，所以抛错后本轮同步被记为失败：`channels.json` 没有写入，没有广播，也没有 `RATIO_ALERT` 和 Telegram 推送。5 秒后的下一轮同步把新数字补上，但提醒和倍率历史已经丢了。直接同步（启动、手动刷新）遇到倍率变化时，整次同步都会返回失败。已改为 `direction: alert.direction`。之前的测试都把 `handleRatioChange` 换成了空函数，所以没有测到这个问题。新增 2 个用例直接运行真实的处理函数，改动前会报同样的 `ReferenceError`。
- **不跟价**：6f3a8b8（09-21）为了不让过期的上游数据盖过手填的倍率，把进价规则改成：没开 `upstream_billing_rate_sync_enabled` 且 `rate_multiplier ≠ 1` 时一律用 `rate_multiplier`。但 Sub2API 的上游计费探测（`/v1/sub2api/billing`，默认 30 分钟一次）对没开同步的账号也照常更新 `upstream_billing_probe`，只是不改写 `rate_multiplier`。所以对这类账号，塔台就看不到上游改价了。
- **新规则**（`syncRealSub2APIAccounts` 的查询、`executeControlPlaneSafetyPlan` 的 `currentCostSql`、`remoteEffectiveCostSql` 三处保持一致）：
  1. 开了自动同步：用上游价。
  2. 没开，但 `upstream_billing_probe.status = 'ok'` 且 `fresh_until` 还没到（Sub2API 写入的是收到时间加两个探测周期）：仍用上游价。
  3. 否则用 `rate_multiplier`。
  4. 它还是默认值 1 时，退回上游最后一次报的价。

  `fresh_until` 要先用正则确认是时间格式，再在 `CASE` 里转成 `timestamptz`。PostgreSQL 不保证 `AND` 两边的求值顺序，这样写可以保证坏数据不会让整条查询报错。
- **验收**：`npm test` 179/179。把三处的真实 SQL 放到按 Sub2API 表结构手写的本地 PostgreSQL 18 上，跑了 12 种探测状态：开或没开同步、上游价有效或已过期、查询失败、不支持、探测已关闭、时间带 9 位小数、不带小数、带 `+08:00` 时区、格式错误、缺少 `fresh_until`、倍率为默认 1。三处算出的进价都一致，安全动作 SQL 复核时也没有判为过期。上线前在生产库只读核对过：规则改变后进价会变的账号，新进价都不高于所在分组的售价，不会触发自动停用。

## 在用上游被墓碑误挡（2026-09-26）

线上日志反复出现「[自动抓取] 抓取新上游 https://<上游地址> 失败: 上游供应商 [通用上游 (<域名>)] 已被墓碑标记为已删除/已欠费下线」，但 Sub2API 里这个地址还有在接单的账号。只读核对了塔台的墓碑名单、上游供应商列表、账号列表和 Sub2API 的账号表，过程如下：

1. 这个地址原来只有一个账号。它被删掉后，几分钟内同一个地址又建了一个新账号，名字不同。
2. 这几分钟里的一次同步中，`syncRealSub2APIAccounts` 发现这个地址没有账号了，就把自动发现的供应商面板一起清掉，并调用 `tombstoneChannel` 写下三样：地址、旧账号名、面板名 `name:通用上游 (<域名>)`。
3. 新账号出现后，同步只拿这个账号自己的 `base_url` 和名字去调用 `removeTombstone`。地址记录清掉了，旧账号名和面板名留了下来，因为它们和新账号名互不包含。
4. `autoDiscoverAndSyncUpstreamPanelsFromBackend` 给这个地址重新生成的面板名，和留下的那条一模一样。`syncSingleUpstreamPanel` 的规则是地址或名字命中一个就挡，所以每次都拒绝，面板加不回来。这个上游的余额同步、低余额提醒和新 Key 发现因此全部停止。

生产名单里另有一条同样的面板名，它对应的地址上还有一个停用中的账号。那家上游不是 Sub2API 系统，自动发现本来就会跳过，所以日志里没有出现。

另外，旧规则用双向包含来匹配：名单里一条很短的名字（生产名单里有一条只有一个汉字）或很短的域名，会挡住所有名字或地址里含有它的上游。`removeTombstone` 也按包含来清，一个在用账号可能把名字相近的已删除上游一起放出来。

改法（`upstream_scanner.js`，外加 `syncRealSub2APIAccounts` 一处）：

- **按地址认上游**：新增 `upstreamHostKey`，取域名加非默认端口，不分大小写，忽略路径和 `www.`。`isTombstoned` 拿到地址时只比地址，而且要完全相同。没有地址时才按名字比，名字也要完全相同（去掉首尾空格、合并连续空格、不分大小写）。名单的存储格式没变，旧记录照常生效。
- **在用的上游一律放行**：`isTombstoned` 先查本地账号列表 `state.channels`，也就是 Sub2API 里 `deleted_at IS NULL` 的账号。地址上还有账号就直接放行，不用等同步去清名单。
- **按地址清理**：`removeTombstone` 会清掉三类记录：同一地址的记录、同名记录，以及形如「名称 (域名)」且括号里正好是这个地址的面板名。`syncRealSub2APIAccounts` 对每个在用账号都调用一次，没有可清的记录时不写盘。
- **待确认事项**：`tombstoneChannel` 会顺带清掉相关的待确认事项（`dismissActionsForChannel`）。现在只清同一地址或同名的，不再误清别的上游的。

验收：`npm test` 188/188。新增 `scripts/test-upstream-tombstones.js` 8 个用例，另有 1 个旧用例改了断言：它原来要求只有被挡的账号才调用 `removeTombstone`，现在每个在用账号都会调用。新增用例里有 6 个在改动前的代码上失败，其中自动发现那个用例报的就是线上这句错误。另外 2 个检查已删除的上游仍然被挡，改动前后都通过。上线前用生产上的名单和在用账号只读回放了一遍：改动前有两个在用地址的面板名被挡，改动后一个也没有；已删除的地址改动前后都被挡；部署后第一次同步只会清掉这两条面板名。

## 角色范围：只有主调接单，备用就是关掉（2026-09-27）

用户反馈：把通道放进备用后，它还在接单。只读核对生产库（分组、`account_groups.priority`、`accounts.priority`、`schedulable`，以及 `usage_logs` 近 24 小时的请求数）后确认：有几个标着备用（100）的账号，接单开关还开着，而且一直在接单。有一个分组新设的主调几乎没接到单，请求都落在备用上。

原因有三层：

1. **Sub2API 的派单规则**：OpenAI 类账号走 `openai_account_scheduler.go` 的打分选号。优先级只是分数的一项（默认权重 1.0，另外还有负载 1.0、排队 0.7、失败率 0.8、首字 0.5），之后在前 7 名里按分数加权随机，另有会话粘连（session_sticky 3.0、previous_response 5.0）。开着接单开关的账号全都参与分配。主调 1、副调 10、备用 100 同时开着时，新请求大约按 4:4:2 分配。粘连的老会话会一直留在原账号上，直到这个账号不再可调度（`IsSchedulable()` 为假时才会清掉粘连）。Anthropic 类账号按优先级分层，但最前面一层满载时也会往后分。结论是只有关掉接单开关，账号才会真的不接单。
2. **塔台一直在“多主分流”模式**：09-24 合并线上改动时带进了 `singleActiveExclusive = false`，启动和保存设置时都会强制设成这个值。在这个模式下：`setRemoteAccountRole` 把副调、备选、备用都设成可调度；接入上游新 Key 时，备用也是可调度；自动切号只把故障源降到优先级 10，账号仍然开着（只有欠费或人工停用才关）；按成本定性时，副调、备选、备用也开着。
3. **分组里的角色按钮**（`setChannelRole` 带 groupId 的分支）只改 `account_groups.priority` 和 `accounts.priority`，不动 `schedulable`，原来开着的账号仍然开着。拆分共享账号（09-24）时，拆出来的账号照抄原账号的 `schedulable` 和全局优先级，标着备用的也照样开着。自动切号只写 `accounts.priority`，控制台按 `account_groups.priority` 显示角色，所以切换后两边对不上。

改法：

- `routing-policy.js`：新增 `ROLE_PRIORITY`、`ROLE_LABELS`、`roleForPriority`、`groupRole`。角色一律按分组里的优先级（`account_groups.priority`）算：≤1 主调，≤10 副调，≤20 备选，其余是备用。
- **只有主调开着接单开关**：分组角色按钮、不带分组的角色设置、分组编排、按成本定性、接入新 Key 和拆分共享账号，都按角色写 `schedulable`，并同时写 `accounts.priority` 和 `account_groups.priority`。组内角色按钮在事务里再核一次：不能关掉分组里最后一个在接单的账号（`relay-tower: last serving account`）。共享账号的接单开关是整个账号共用的，只有在各分组里“是不是主调”都一致时才能改；不一致时拒绝，并提示先拆分。
- **自动切号**（`auto-failover-policy.js`）：备用不再当候选。候选顺序固定为角色优先（主调 → 副调 → 备选），同一角色内按进价，去掉了 `candidateOrder` 选项。`executeAutoSwitch` 会拒绝把备用当目标。故障源（非共享、非关键字例外）接过目标原来的角色：目标是备选时源就变成备选，否则变成副调。源的接单开关关掉，两边的优先级字段一起写。日志里新增 `fromNewRole`。预演和保护情况把备用标成「备用（已关闭，自动切号不用它）」，不算能顶上的账号。网关同一请求内的后备重试也不会用备用。
- **解除人工停用**（`/toggle`、`/batch/toggle`）：只有在某个分组是主调的账号才会打开接单开关，也只核这些账号的进价。其余账号只清掉人工停用标记。返回的提示按角色说明结果。
- **一次性清理**：`GET /api/role-check` 列出“标着副调、备选或备用，接单开关却开着”的账号。只在一个分组、而且这个分组里还有别的主调在接单的账号，标为可关。`POST /api/role-check/fix` 只关用户勾选、而且仍然可关的账号，同一事务里再核一次：角色没变、只在这个分组、分组里还有别的主调在接单。控制台顶部有黄色提示条，账号行上有「标着备用却在接单」的标记。重复点当前的非主调角色，也会重新执行一次，把接单开关关掉。

- 行上的人工停用开关原来是一个没有样式的 checkbox（`switch-control` 和 `slider` 在 CSS 里没有定义）。现在换成写着「关闭 / 打开」的按钮（`.btn-strip-power`），下面显示状态：接单中、待命、暂停中、已关闭、手动关闭。关闭正在接单的账号前会先确认；如果它是某个分组里唯一在接单的，确认框会说明关掉后会怎样。分组卡片下方加了一句规则（`groupRuleLine`），和服务端 `isExemptGroup` 一样区分三种情况：总开关关闭、人工管理分组、普通分组。
- 会被自动打开的情况只有以下几种，全部来自 `evaluateGroup` 和 `executeAutoSwitch`：
  1. 主调出故障时，按顺序打开副调，再打开备选。
  2. 原主调恢复后切回（`main_recharged`）。
  3. 分组里一个接单的都没有时（`no_active_account`），按 主调 → 副调 → 备选 的顺序打开一个能用的。
  4. 分组开了「便宜账号自动换过去」时，换到更便宜的副调或备选。

  备用、手动关闭的账号，以及人工管理分组里的账号，都不会被自动打开。Sub2API 自己只会在出错时把 `schedulable` 设成 false，从不自动打开。

## 本组找不到账号接单也算主调出问题（2026-09-27）

用户问：主调出了什么情况，副调才会被打开？按 09-24 定的阈值（失败率 70%、样本 20、连续失败 30、探活连续失败 10、冷却 10 分钟）和小流量站点的实际情况（5 分钟窗口里往往只有几次请求），失败率、连续 30 次和首字这几条基本凑不够。实际会触发切换的是：欠费（余额每 10 分钟同步一次）、小流量规则（窗口内连续 3 次真实失败，2 分钟内补一次真实生成探测，探测也失败）、`/v1/models` 连续 10 次失败（每 60 秒探一次）、账号在 Sub2API 被停用或出错、人工关闭、分组里没有账号在接单。

漏洞：Sub2API 选不出账号时，报错写进 `ops_error_logs`，其中 `error_phase='routing'`、`error_owner='platform'`，`group_id` 有值，`account_id` 大多为 NULL。常见原因有四种：

- 所有账号都不可调度：返回 503「Service temporarily unavailable」或「No available accounts」。
- 本组没有账号支持这个模型：返回 404 `model_not_found`。
- 全部账号被限流：返回 429。
- 并发满且没有排队计划，或者全部候选被利润控制拒绝：这两种 `account_id` 可能有值。

`fetchRecentFailoverMetrics` 只统计 `account_id IS NOT NULL` 的记录，所以主调缺模型、被 Sub2API 暂时冷却时，塔台看不到这些故障，也就不会打开副调。已核对 Sub2API 源码：`error_phase='routing'` 只会写在上面这几种情况，客户自己被限流、欠费、Key 失效、请求格式错误、等待账号并发超时都不会写成 `routing`。`model` 和 `requested_model` 是客户原样请求的模型名。

改法：

- `fetchRecentGroupRoutingFailures`：单独一条查询，缓存 30 秒，出错时返回空、只记日志，不影响按账号的统计。按分组取近 5 分钟 `error_phase='routing'` 的记录（时间、模型、`error_type`），以及本组近 5 分钟最后一次成功请求（`usage_logs`）的时间。
- `evaluateGroup`（`groupMetrics`）：`runtime.currentSince` 记下当前账号从什么时候开始当主调。只统计同时晚于这三个时间点的 routing 报错：它当上主调的时间、上次切换的时间、本组最后一次成功请求的时间。达到 `routingFailuresThreshold`（默认 3）次，就把当前账号判为 `routing_failures` 故障，照常按 副调 → 备选 的顺序切换，并要求之后用真实生成探测证明它恢复了。
- `model_not_found` 只在两个条件同时满足时才算：主调的模型映射里没有这个模型，而且本组有别的能顶上的账号支持它。顶上的账号必须支持这些模型。主调因为缺模型被换下后，`routingModels` 会记下缺的模型；它的模型映射里补上这些模型之前，不会被判为已恢复。
- 预演和原因名称里加了 `routing_failures`；当前账号的说明里显示「本组最近 N 次请求找不到账号接单」。

验收：`npm test` 207/207，新增 5 个用例：

- 连续 3 次时切换，2 次时不切。
- 本组之后有成功请求、上次切换之前、刚当上主调之前的报错都不算。
- 缺模型只在别的账号能接时才算，顶上的账号必须支持该模型。
- 缺模型被换下的主调，补上模型后才切回。
- 查询只认 `error_phase='routing'`，会缓存，出错时返回空。


## 替补只看客户在用的模型；没替补时每小时提醒；为省钱换号前看最近报错（2026-09-29）

用户反馈：某个分组的主调上游出了故障，一整晚没有自动换号，也没收到提醒。我们只读核对了生产库和塔台数据，原因有三层：

1. **分组里没有能用的替补。** 其余账号都是备用（关掉），自动切号不会用它们。这是配置问题，已经告诉运营者。
2. **模型要求过严。** `requiredModels` 取当前主调的整张模型表（`configuredModels`，或 `modelMapping` 的键），候选账号必须支持其中每一个。主调表里有一个近 7 天没人请求过的模型，本组其他账号都没有。所以第二天上午副调已经设好、主调再出问题时，决策仍是 `exhausted`。
3. **提醒只发一次。** `exhaustedNotified` 只在切换成功后才清掉。前一天已经提醒过一次，所以这一晚的故障在控制台和 Telegram 上都没有任何提醒。

另外，这个分组开着 `autoRecoverLowestCost`。运营者手动把客户换走后，`cheaper_recovered` 几分钟后又把客户切回这个更便宜的主调。它的 `/v1/models` 探测和 1 token 生成探测都正常，但真实请求仍在报错：
- 上游对其中一个模型回 404，Sub2API 就把这个模型在该账号上锁 30 分钟（`extra.model_rate_limits`），锁着的时候这个模型的请求全部返回 routing 503。
- 另一个模型间歇性返回 502。

改法：

- **`fetchGroupModelDemand`：** 单独查询，缓存 10 分钟；出错时返回空，1 分钟后重试。按分组取近 7 天 `usage_logs` 和 `ops_error_logs` 里客户请求的模型，取法是 `COALESCE(NULLIF(btrim(requested_model), ''), model)`。`status_code = 404` 的不算，因为那是本组没人支持的模型。结果按请求次数从多到少排。
- **`requiredModels(current, group, demand)`：** 分组声明了模型表时照旧。否则取当前账号模型表与 demand 的交集，按 demand 的顺序排。没有 demand 数据，或当前账号不限模型时，行为不变。`missingModels` 导出给预演和提醒用。
- **`fetchRecentAccountErrors`：** 单独查询，缓存 3 分钟；出错时返回空。按账号统计近 6 小时 `ops_error_logs` 中符合两个条件的记录数：`error_owner = 'provider'`，并且 `status_code >= 500` 或属于 401/402/403/404/429。客户自己的错不算，重试后成功（200）的也不算。
- **`evaluateGroup`：**
  - 判出 `request_failures`、`probe_failures` 或 `routing_failures` 时，记下 `accounts[id].lastFaultAt`。
  - `cheaper_recovered` 跳过 `recentTrouble` 的账号，也就是满足下面任一条件的：近 6 小时上游报错达到 `recentErrorLimit`（3）次；`lastFaultAt` 在 `recentErrorWindowMs`（6 小时）内。
  - 故障换号和 `main_recharged`（原主调切回）不受这条限制。
  - 决策结果新增 `required` 和 `recentTrouble`。
- **`evaluateAutoSwitch`：**
  - `exhaustedNotified` 改为 `exhaustedNotifiedAt`：距上次提醒满 `EXHAUSTED_RENOTIFY_MS`（1 小时）就再提醒一次，切换成功后清掉。
  - 读到旧的 `exhaustedNotified` 字段就删掉，分组不会再因为它一直不提醒。
  - 提醒里点名缺模型的副调和备选。
- **预演：** 非当前账号缺模型时写明缺哪些，并且 `candidate` 设为假。有 `recentTrouble` 时写明报错次数；分组开了便宜优先时，再加一句「暂不为省钱换过去」。
- **控制台：** 保护情况把缺模型的账号单独归类。说明文字同步更新，`app.js` 版本号改为 `20260929_failover_models`。

验收：

- 两条新查询在生产库只读执行通过。

## 刷新余额后过一会儿又跳回旧金额（2026-09-30）

用户反馈：点「同步上游余额」后账号余额是对的，过一会儿又变回之前欠费时的金额。只读核对生产数据和日志，找到两层原因。

1. **面板里的钱包余额是冻结的快照。** `syncSingleUpstreamPanel` 开头是 `let userInfo = params.userInfo || null`，而下面每一种查余额的办法（`/api/v1/auth/me`、`/api/user/self`、`/v1/dashboard/billing/subscription`、`/v1/usage`）都带着 `!userInfo` 条件。面板对象自带上次存下的 `userInfo`，所以这几步全被跳过，结果原样返回，`lastSyncTime` 照常刷新，状态还是 `connected`。登录账号密码的面板不受影响：会话探活会重新读出 `userInfo`。只有 API Key 接入的面板（自动发现建出来的，`userToken` 是 `sk-` 开头的 Key，没有账号密码）第一次同步之后再也读不到新余额。线上这样的面板，有的存着比实际高出很多的数，有的存着比实际低很多的数，同一个面板连续两次同步的余额一分不差，只有同步时间在变。
2. **旧快照有三条路写进账号：**
   - `syncSingleUpstreamPanel` 末尾把余额写进这个地址下的所有账号。每 10 分钟的 `refreshAllBalances` 先同步全部面板，再逐个账号用自己的 Key 查 `/v1/usage`。生产上按 2 秒间隔观察到：面板同步的瞬间，一批账号的余额被改成面板里的旧数，约 4 秒后才改回来。这几秒里还会广播 SSE，自动切号开着时还会触发一次 `evaluateAutoSwitch`。
   - 直接调用的 `syncRealSub2APIAccounts()`：只要账号匹配到面板，就用面板的 `userInfo.balanceUSD` 盖掉账号现有余额，不看谁更新。它在改分组、调角色、「同步后台」、单个账号测速时会被调用，`upstream_scanner.js` 的 `runScan` 一开头也调用它，也就是每 3 小时一次的巡检，以及每次在「上游供应商后台」里添加或同步面板之后。盖掉之后要等下一次 `refreshAllBalances` 才恢复。后台控制面 worker 的合并跳过 `balance*` 字段，不受影响。
   - `fetchChannelBalance` 里账号自己的 Key 查不到时退回面板；同步后没有重新取列表里换上的新面板对象，读的是旧对象。

改法：

- **`syncSingleUpstreamPanel`：** `userInfo` 每次从空开始读，上次的值单独放在 `previousUserInfo`，读不到时才退回它，并把结果标成 `balanceStale: true`。凭模型列表占位的 `balanceUSD: 0` 也算「没读到」。`balanceStale` 的面板不写进任何账号；同步整个失败时写进面板列表的记录也带 `balanceStale: true`。登录受限时不再直接采用旧值，先用上次的凭据再读一遍。
- **`syncRealSub2APIAccounts`：** 面板余额只在两种情况下采用：账号没有余额读数（`balance` 为空且不是不限额），或面板 `lastSyncTime` 晚于账号的 `balanceUpdated`。`balanceStale` 的面板一律不用。网关记下的欠费会把 `balanceUpdated` 设成当时的时间，所以同样不会被更早的面板数顶掉。
- **`fetchChannelBalance` / `applyChannelBalanceInfo`：** 退回面板时结果带 `source: 'panel'`，并读列表里最新的面板对象；`balanceStale` 的面板不算读数。新增 `applyChannelBalanceInfo`，整批刷新和单个账号刷新共用：`source: 'panel'` 的结果读取时间不晚于账号现有读数时不写，账号自己 Key 查到的数一律写。单个账号刷新遇到不采用的情况，回给页面的是账号现在的读数。
- 没有新增账号字段，`CONTROL_PLANE_LOCAL_CHANNEL_FIELDS` 不用改。顶部「上游备付金」是把面板余额加起来的，面板不再冻结，它也就跟着准了。

验收：
- `npm test` 227/227。新增 10 个用例：面板每次重读余额、读不到时标 `balanceStale` 且不写账号、真读到的写进本地址的账号、同步失败标 `balanceStale`、账号同步不覆盖更新的读数和网关欠费记录、面板更新时才采用、不用 `balanceStale` 的面板、兜底只用真读到的面板、`applyChannelBalanceInfo` 的先后规则。前 8 个在改动前的代码上有 7 个失败，剩下 1 个是对照用例。
- 生产只读核对：每个面板的 Key 与该地址下账号的 Key 是否同一把（只比较指纹）、各上游 `/v1/usage` 实际返回、2 秒间隔观察一次 10 分钟同步里账号余额被改成旧数又改回来的全过程。全程没有写入生产数据。

## 客户用量与模型利润（2026-09-30）

用户需求：知道每个客户用了多少量、用了哪些模型、产生了多少利润。原来的「用户财务」窗口只有每个客户的累计消费和利润，没有 tokens，也看不到分模型的数字。

口径：

- **和财务大盘一致。** 客户消费 = `usage_logs.actual_cost`；采购成本 = `total_cost × 账号倍率`，倍率的取法（`account_rate_multiplier` 快照，快照为空或为 1 时取账号现在的 `rate_multiplier`，再没有就是 0）和 `fetchUserFinancialStats` 里 `normalized_usage` 的 `effective_cost` 一字不差；利润 = 两者之差，毛利率 = 利润 ÷ 客户消费。
- 总 tokens = 输入 + 输出 + 缓存写入 + 缓存读取，和 Sub2API 的 `UsageLog.TotalTokens()` 相同。请求次数是成功计费的请求数（失败的请求不写 `usage_logs`）。
- 模型名取 `COALESCE(NULLIF(btrim(requested_model), ''), NULLIF(btrim(model), ''), '未记录模型')`：客户请求里写的名字，和自动切号统计客户请求过哪些模型的口径一致。
- 时间范围「今天 / 昨天 / 近 7 天 / 近 30 天」的算法和大盘一样：自然日按数据库时区，「近 N 天」是滚动 N×24 小时。另有「本月」（本月 1 日 0 点起）和「全部」。已删除的客户、管理员和测试号的用量也在结果里（大盘的合计同样不排除已删除客户），页面上按「外部客户」的规则筛选，规则和「用户收支明细」页签一致。

改法：

- **`user-usage.js`（新）：** 时间范围只能取自写死的白名单 `USAGE_RANGES`，SQL 里拼进去的都是常量片段，前端传来的任何文字都进不了 SQL。`buildUserUsageSql` 每个「客户 × 模型」返回一行汇总；`buildUserUsageReport` 整理成 客户 → 模型，客户按利润从高到低、模型按消费从高到低，并算出每个客户和全部客户的合计、毛利率、模型占比（客户一分钱没花时占比按请求次数算）。`EFFECTIVE_COST_SQL` 是采购成本算法的唯一一份，测试核对它和大盘里的一致。
- **`server.js`：**
  - `execPsqlAsync`：异步子进程连同一个 Sub2API 库，查询期间不阻塞事件循环（同步的 `execPsql` 会卡住网关转发）。用 `PGOPTIONS` 让数据库自己限时（`statement_timeout`，默认 20 秒）并强制只读（`default_transaction_read_only`），因为只杀本地的 docker 命令，库里的查询还会接着跑。输出超过上限、进程报错、超时都会明确报错；SSH 方式下每个 docker 参数都加引号。
  - `fetchUserUsageReport`：按时间范围缓存 30 秒；同一范围同时来多个请求共用一次查询；失败不缓存。
  - `GET /api/user-usage?range=`（需要登录，`refresh=true` 跳过缓存）：范围不认识返回 400；数据库出错返回 500 和一句大白话，控制台其它功能不受影响。这个查询是按需的，不放进后台定时任务。
- **控制台：** 「用户财务」窗口新增页签「用量与模型利润」（`index.html`、`app.js`、`style.css`）：时间范围、外部客户 / 全部用户、搜索、排序、刷新；顶部合计；每个客户一行，点开看分模型明细；亏本的客户和模型标红。「用户收支明细」每个客户名下加一个小链接跳到这里，该客户是测试号或管理员时自动切到「全部用户」。快速切换时间范围时只认最后一次请求的结果；读取失败时保留原来显示的数据，只在状态行提示。邮箱、模型名一律按文字显示。`style.css` 和 `app.js` 版本号改为 `20260930_user_usage`。

## 手动选的主调被为省钱换号换走，两条规则来回倒（2026-10-02）

用户反馈：一个分组的主调账号上游出了问题，手动把另一个账号设成主调、有问题的设成副调，系统一会儿又把有问题的账号调回来了。只读核对线上记录，时间线是：

- 手动改完 40 秒后，`cheaper_recovered` 把客户换回有问题的账号（它的进价比现在的主调低）。
- 10 分钟后（`cooldownMinutes`），`main_recharged` 又把客户换回运营者选的账号：运营者手动设主调时，`manualLocked` 让原主调记录改成了这个账号。
- 再过 10 分钟冷却结束，又会是 `cheaper_recovered`。用线上数据空跑：旧规则会换，新规则按住。分组开着便宜优先，所以两条规则一直轮流触发。

原因：

1. **为省钱换号没有人工选定的保护。** `cheaper_recovered` 的目标只要 `recovered`（连续 3 次 `/v1/models` 探测正常，持续 3 分钟）、不是 `recentTrouble`（近 6 小时上游报错 3 次，或塔台 6 小时内判过它故障）。有问题的账号已经很久没接过任何请求，`/v1/models` 探测一直正常，塔台上次判它故障也早已超出 6 小时的窗口。没有请求就没有证据，上次加的 `recentTrouble` 保护看不到它。
2. **`main_recharged` 和 `cheaper_recovered` 互相抵消。** 原主调比别的账号贵、分组又开着便宜优先时，每次切换后都是：冷却一过，原主调恢复，`main_recharged` 回切；再冷却一过，`cheaper_recovered` 换走。两条规则都合规则，合在一起就是无限循环。

改法（`auto-failover-policy.js`）：

- **`originalMainManual`：** 新的运行时标记，记下「原主调是不是运营者亲手选的」。记下原主调时，`current.manualLocked === true` 就是 `true`，否则是 `false`；沿用旧记录时保持原值。没有这个字段的旧记录按 `true` 算（`originalMainIsManual`），宁可少换一次号。
- **`cheaper_recovered`：** 找到更便宜的恢复账号后，如果当前主调就是原主调、且 `originalMainManual` 为真，返回 `hold` / `manual_main`，不换。故障切换和 `main_recharged` 不受影响：手选的主调出故障，照常换走；换走后恢复，照常换回来，并且换回来后依然受保护（标记存在运行时里，不依赖 `manualLocked`；换号时 `executeAutoSwitch` 会清掉账号上的 `manualLocked`）。
- **为省钱换号后改记原主调：** 从原主调（不是人工选的）换到更便宜的账号时，`originalMainId` 改成新主调，`originalMainManual` 为 `false`。这样冷却结束后 `main_recharged` 不会再把它换回原来更贵的账号。从顶班账号换到更便宜的账号，不动原主调记录。
- **预演和说明：** `AUTO_SWITCH_REASON_NAMES` 新增 `manual_main`（「主调是你亲手选的，不为省钱换号」）。控制台里「更便宜的账号恢复后，自动换过去」的说明写明这一点，并提醒想让账号彻底不接单要设成「备用」。

验收：

- `npm test` 268/268。新增 7 个用例：`test-auto-failover-policy.js` 用一个按塔台实际落地方式回放几十分钟的小函数（`replay`）覆盖：手选主调不被换走、对照组照常省钱换号、没有更便宜的账号时原因仍是「运行稳定」、手选主调出故障照常故障切换、故障换走后充值换回来仍受保护、不是人工选的主调只换一次不再换回来、旧记录按人工选的算、顶班账号照常省钱换号、新手选的主调替换原主调记录；`test-regressions.js` 检查预演写明原因，并有不是人工选定时会换过去的对照。除「手选主调出故障照常切换」是保护性用例外，其余在改动前的代码上全部失败，旧代码的失败内容正是 `cheaper_recovered → main_recharged → cheaper_recovered` 的循环。
- 用线上数据空跑（只读，把新规则的代码通过标准输入送进容器，不写任何文件）：冷却中两个版本都是 `hold`；冷却结束后，旧规则 `switch` / `cheaper_recovered` 换到有问题的账号，新规则 `hold` / `manual_main`。

部署时注意到：最近两次重启，日志都先是「❌ [Telegram] 初始化连接失败:」（后面是空字符串），10 秒后重试才连上。只读排查（容器内）：

- 容器里是 Node v22.23.2，`net.getDefaultAutoSelectFamily()` 为 `true`，`getDefaultAutoSelectFamilyAttemptTimeout()` 为 250 毫秒。
- `api.telegram.org` 同时有 A 和 AAAA 记录，`dns.lookup` 先给 IPv4。容器没有 IPv6：连 IPv6 地址直接 `ENETUNREACH`。
- 平时到 IPv4 地址的 TCP 握手约 150 毫秒；第一次 HTTPS 请求约 490 毫秒，之后约 150 毫秒。
- 复现：把 `autoSelectFamilyAttemptTimeout` 压到 10 毫秒，`https.request` 报 `AggregateError`，`code` 为 `ETIMEDOUT`，`message` 为空，内层是 `ETIMEDOUT`（IPv4）和 `ENETUNREACH`（IPv6），和线上日志一致。

原因：服务刚启动时第一次握手超过 250 毫秒，happy eyeballs 放弃 IPv4 改试 IPv6，IPv6 立即失败，抛出 `message` 为空的 `AggregateError`；`start()` 只打印 `e.message`，所以日志冒号后面是空的。

改法（`upstream-monitor/telegram.js`）：

- `apiRequest` 的请求选项加 `autoSelectFamilyAttemptTimeout: 3000`。
- `start()`：失败后按 3、6、12、24、48、60 秒重试（`telegramRetryDelayMs`），用 `isStarting` 防止并发启动；前两次失败记 `console.warn`，连续 3 次以上记 `console.error`；成功时注明是第几次尝试。`stop()` 清掉待执行的重试。
- `describeNetError`：拼上 `code` 和 `AggregateError.errors` 里每个地址的错误码与地址。

验收：`scripts/test-auth-telegram.js` 新增 2 个用例（请求选项里每个地址至少等 2 秒；启动遇到空消息的 `AggregateError` 时 3 秒后重试、日志写明各地址原因、只记提醒，第二次成功后开始轮询）。

## 双机集群中台重做（2026-10-09）

## 原主调因为客户请求出错被换下后，每过一个冷却就被换回去（2026-10-09）

只读核对线上换号记录：有的分组从前一天下午起每 10 到 40 分钟来回换一次。原主调接单就出错，`request_failures`（偶尔是 `routing_failures`）把它换下；它不接单之后没有客户请求，`/v1/models` 探测和 1 个字的生成探测都正常，3 分钟后判为 `recovered`，10 分钟冷却一过，`main_recharged` 又把它换回来。

原因：`main_recharged` 只看原主调现在是否 `recovered`，不管它是为什么被换下的。欠费换下的账号，充值后探活正常就能证明恢复；请求出错换下的账号，探测通过证明不了客户的真实请求能成功。

改法（`auto-failover-policy.js`）：

- **`lastRequestFaultAt`：** 每个账号的运行时观察新增这一项。`request_failures` 时记下；`routing_failures` 只在算进去的报错里有不是「模型不支持」的（`routingEvidence` 新返回 `otherCount`）时记下。欠费、人工停用、`probe_failures` 不记。没有这个字段的旧记录用 `lastFaultAt` 补上（宁可晚点换回），之后字段一直存在（没有就是 `null`）。
- **`originReturnHoldMs`（默认 6 小时）：** `main_recharged` 找到已恢复的原主调后，如果它的 `lastRequestFaultAt` 还不到这么久，不换回，记下 `heldOrigin = { id, until }`。后面的 `cheaper_recovered` 照常判断（它本来就避开 `recentTrouble` 的账号）；最后没有可换的，原因是 `origin_recent_failures`，不再写「运行稳定」。
- **故障切换不变：** 顶班的账号自己出故障时，原主调只要 `available` 照常可以被换上来，这个限制只管主动换回。
- **`returnAfter`：** 因为请求出错换下原主调的那一次决策，返回它最早什么时候会被自动换回（`now + originReturnHoldMs`），`server.js` 把它写进换号记录，Telegram 推送里据此写一句「几点以后才会自动换回」。
- **文字：** `AUTO_SWITCH_REASON_NAMES.main_recharged` 改成「原主调恢复正常」，新增 `origin_recent_failures`；Telegram 换回标题改成「原主调恢复了，已自动换回」；自动切号预演里，被按住的原主调写明换回时间。
- **换号流水标签（`public/app.js`）：** `autoSwitchLogTag` 按 `triggerType` 查表。以前只认 `balance_empty`、`provider_error`、`hard_down`、`cost_recovery`、`auto_recover_lowest_cost`、`manual_test`，现在的 `request_failures`、`routing_failures`、`probe_failures`、`main_recharged`、`cheaper_recovered` 都落到默认的「首字超时」。`app.js` 版本号改为 `20261009_switch_tags`。

## 「出字太慢」被零星几个特别慢的请求触发（2026-10-09）

只读核对线上换号记录和请求日志：前一天有几次换号的原因是最近 5 分钟的平均首字时间超过 30 秒，但这些账号同一段时间里大多数请求几秒就出字，平均值是被少数几个特别慢的请求拉上去的（超长的提示词本来就要一两分钟才出第一个字）。同组的另一个账号也有这样的慢请求，换过去不会更快，只会多一次来回换号。

原因：`evaluateGroup` 用 `avgTtftMs > ttftThresholdMs` 判「出字太慢」。平均值对极端值很敏感，几个等了两三分钟的请求，就能把三十几个几秒出字的请求的平均值拉过 30 秒。

改法：

- **生产统计（`server.js` 的 `fetchRecentFailoverMetrics`）：** 多算一列 `percentile_cont(0.5) WITHIN GROUP (ORDER BY ttft)`，返回 `medianTtftMs`。失败的请求没有首字时间（`ttft` 为 `NULL`），和平均值一样不算在内；一个带首字时间的请求都没有时为 `null`。
- **塔台网关统计（`gateway.js` 的 `GatewayMetrics.summary`）：** 同样给出 `medianTtftMs`，偶数个时取中间两个的平均。
- **判定（`auto-failover-policy.js`）：** 有中位数时拿中位数和 `ttftThresholdMs`（仍是 30 秒）比，也就是一半以上的请求都等过了阈值才算；统计里没有中位数（老的数据来源）时退回平均值。最少样本数、失败率、连续失败这些条件都不变。
- **没改的：** 控制台上展示的「平均首字」仍是平均值，只是展示用；阈值设置项不变。
