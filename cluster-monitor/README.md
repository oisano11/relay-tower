# 双机集群中台

监控两台服务器（主节点、副节点）的运行状况。主节点上跑 `hub.py`，副节点上跑 `agent.py`，
数据最后在中转塔台的「双机集群状态」面板里显示（需要登录）。

## 设计原则

- **只读。** 中台和 agent 只读 `/proc`、`docker ps`、`docker logs`，做一次本机健康检查，再用 TCP 连一下对端的端口。不 SSH，不执行外部输入。
  注意：运行账号需要在 docker 组里才能读到容器状态，而 docker 组本身等同于 root 权限。所以运行账号要专用，只用于这一件事。
- **只有一个接口。** 中台只提供 `GET /api/status`，agent 只提供 `GET /snapshot`。没有页面，没有 CORS，不接受 POST。
- **必须带令牌。** 每个请求都要 `Authorization: Bearer <令牌>`。令牌没设、太短（少于 24 个字符）或全是空白，都拒绝启动。
- **不挂公网。** `HUB_BIND` 必须设置，填中转塔台容器能访问的 Docker 网关地址，不能是 `0.0.0.0`。agent 的 `AGENT_BIND` 填副节点在隧道上的地址。
- **取不到就说取不到。** 读不到的值一律是 `null`，界面显示「取不到」。数据超过 1 分钟没有更新，就当作过期：不显示旧数字，诊断也不给 PASS。
- **地址和名字不进代码。** 所有地址、标签、令牌都来自环境变量，示例见 `config.example.env`。

## 文件

| 文件 | 作用 |
| --- | --- |
| `hub.py` | 主节点：后台每 `HUB_INTERVAL_SECONDS` 秒采一次，接口返回最近一次结果；隧道用 TCP 检查 |
| `agent.py` | 副节点：后台每 `AGENT_INTERVAL_SECONDS` 秒采一次，接口返回最近一次结果 |
| `metrics.py` | 指标读取和 TCP 探测函数，读不到返回 `None` |
| `common.py` | 令牌检查、只读 JSON 接口的通用部分 |
| `config.example.env` | 配置示例（IP 是文档保留的示例地址） |
| `systemd/` | 两个服务的模板，`User=` 要改成你自己的运行账号 |
| `backup/db-backup.sh` | 数据库每日备份脚本，在副节点上跑（见下面「数据库备份」） |
| `backup/db-backup.cron.example` | 备份的定时任务示例 |
| `tests/` | Python 单元测试和本机 HTTP 测试 |

中转塔台这一侧的代码在 `upstream-monitor/cluster-status.js`（取数、状态判断、报警判断）和
`upstream-monitor/public/cluster-view.js`（面板渲染，所有来自服务器的文字都先转义）。

## 部署（还没有部署，需要单独批准）

部署的顺序很重要，不能颠倒：

1. **先删旧的反向代理转发。** 如果反向代理里还有旧的集群转发（指向 8899），先删掉。否则中台一启动，旧转发就能把外网请求转进来。
2. **主节点装中台。** 把本目录放到 `/opt/relay-tower/cluster-monitor`，复制 `config.example.env` 成 `/etc/cluster-monitor/hub.env`，
   填好真实值，权限设成 600。`HUB_BIND` 必须填。运行账号要在 docker 组里，并且是专用账号。`systemd/cluster-hub.service` 改好 `User=` 后启用。
3. **副节点装 agent。** 同样放好文件，`/etc/cluster-monitor/agent.env` 里 `AGENT_BIND` 填副节点在隧道上的地址（和主节点的 `WORKER_AGENT_URL` 里的 IP 一致），
   `AGENT_TOKEN` 和主节点的 `WORKER_AGENT_TOKEN` 一样。启用 `systemd/cluster-agent.service`。
4. **中转塔台。** 在和 compose 文件同一个目录的 `.env` 里写入 `CLUSTER_HUB_URL`（中台的 Docker 网关地址）和 `CLUSTER_HUB_TOKEN`（和 `HUB_TOKEN` 一样）。
   **同时必须保留 `DOCKER_GID`**：独立目录的 compose 要求它，而目录里一旦有了 `.env`，部署脚本就不再自动补它。`.env` 权限设成 600。
   没有设置时面板显示「未配置」，启动日志里会说明报警没有启动。
5. **收回旧的 SSH 钥匙。** 旧方案从主节点用 root 账号 SSH 连副节点，那把钥匙在两台机器上都要删掉。
6. **旧服务。** 如果机器上还有旧版本的服务单元，确认它已经停止、禁止开机启动后再删掉。

## 怎么验证

在主节点上（令牌从环境文件里读，不要打印出来）：

```bash
curl -s -H "Authorization: Bearer $HUB_TOKEN" http://172.22.0.1:8899/api/status | head -c 400
```

没有令牌应该返回 401，`/` 应该返回 404，`POST`、`HEAD`、`OPTIONS` 应该返回 405。
面板上隧道那一行应该显示「能通」和一个往返毫秒数；副节点两台都应该有读数。

## 数字的口径

- **近 5 分钟客户请求**：每台各自接了多少、失败多少、成功的一般多久回完。只数路径以 `/v1/` 开头的调用，控制台和网页自己的管理接口也写进同一份日志，不算在内。每个请求只数它的「请求完成」那一行；Sub2API 的 console 和 json 两种日志格式都认。
  - **失败**：状态码 5xx（服务器或上游出错）。4xx 是客户自己的问题（Key 不对、余额不够、被限流），不算失败。
  - **一般多久回完**：成功请求从进来到回完的中位数。流式请求要等整段回答写完，所以比「出第一个字」慢得多。
  - 已经开始往客户那边写回答、写到一半断掉的请求，日志里记的还是 200，这里数不到。
- **分流比例**（主 / 副各占多少）：用两台近 5 分钟的请求数算。2026-10-11 对过账：同一个小时里，两台日志里成功的对话请求加起来和数据库的记录只差 0.5%（差的是回答写到一半断掉、日志里仍记成功的请求）。客户查余额、查用量的请求也走 `/v1/`，也算在请求数里。
- **成功率和报错数**：与主看板的口径一致，近 24 小时，报错只算未处理的。
- **今日请求、今日流水、模型排行**：今天的口径，流水排除内部账号。

## 流量怎么算

- 中台和 agent 只给连外网那块网卡开机以来收、发的总字节数，外加开机时间。网卡默认用默认路由走的那块，要指定就填 `MASTER_NET_IFACE` / `AGENT_NET_IFACE`。
- 中转塔台的报警轮询每分钟记一次，和上一次相减，按北京时间的日期累加，存在数据目录的 `cluster_traffic.json` 里，保留 70 天。
  - 服务器重启后计数器清零：开机时间变了，或者数字变小了，就认出来，这一次从零算起。
  - 中转塔台停了一阵（比如部署）：恢复后第一次相减，会包含停的那段时间，按时间比例分到经过的每一天。
  - 开始记录以前用了多少，不知道，也不估。第一个月的「本月」会注明从哪天开始记。
- **额度：** 面板上点「改额度」，填每台每月多少 GB、每月几号重置，存在数据目录的 `cluster_settings.json` 里。按 1000 进位，收 + 发合计。有的服务商只算发出去的那一半，那样面板上的数会比服务商后台的大，偏保守。
- 两台之间的隧道（主节点的 `wg0`）也记，只看，不算额度：隧道的流量本身也走外网网卡，已经算在两台的流量里了。
- 记满一天以后，估算「照这个速度本月一共大约用多少」：本月已用 ÷ 已经记了多久 × 这个计费月的长度。

## 数据库备份

- **放在哪：** 备份脚本在副节点上跑，从主节点的数据库导出，存在副节点自己的硬盘上。主节点整台出事时，数据还在另一台机器上。
- **什么时候：** 每天一次，示例里是北京时间凌晨 4:30（一天里请求最少的时候）。
- **怎么导：** 用 postgres 官方镜像里的 `pg_dump`（要和数据库同一个大版本，用 `PG_IMAGE` 指定），导成 pg_dump 自己的压缩格式。系统日志表 `ops_system_logs` 只备份表结构、不备份内容（只是排错用的日志，占了数据库一半多），要改就设 `SKIP_DATA_TABLES`。
- **密码：** 数据库的地址、库名、账号、密码，从副节点上 Sub2API 容器的环境变量里读。副节点的 Sub2API 本来就要连这个数据库，所以不新建任何存密码的文件。密码只经环境变量传给 `docker run`，不出现在命令行里。
- **不留半成品：** 先写成隐藏的临时文件，`pg_restore --list` 读得出目录才改成正式的名字；失败了就删掉，旧的备份不动。
- **留几份：** 只留最新的 7 份（`KEEP`）。按份数删，不按天数删：备份连续失败几天，也不会把好的备份删光。硬盘剩余不到 5 GB 就不做（`MIN_FREE_MB`）。
- **谁能看：** 备份目录 root 所有、属组是 agent 的运行用户组、权限 750；备份文件 600，只有 root 能读。agent 只看文件名、时间和大小。
- **面板和提醒：** agent 设了 `AGENT_BACKUP_DIR`，副节点的卡片上就显示最新一份的时间、大小和一共几份；早上 9 点的简报也写一行。超过 26 小时没有新的备份，发一条不响铃的提醒；备份目录连续三次读不到，另报一条。

### 安装（在副节点上，用 root）

```bash
install -m 755 backup/db-backup.sh /usr/local/sbin/sub2api-db-backup
install -m 644 backup/db-backup.cron.example /etc/cron.d/sub2api-db-backup
BACKUP_DIR=/var/backups/sub2api-db READER_GROUP=cluster-agent /usr/local/sbin/sub2api-db-backup
```

最后一行是先手动做一份，确认能成功。然后让 agent 知道备份目录：在 `agent.env` 里加 `AGENT_BACKUP_DIR=/var/backups/sub2api-db`，
或者用 systemd 的 drop-in（`/etc/systemd/system/cluster-agent.service.d/backup.conf`，内容是 `[Service]` 和
`Environment=AGENT_BACKUP_DIR=/var/backups/sub2api-db` 两行），再 `systemctl daemon-reload && systemctl restart cluster-agent`。

### 怎么恢复

先确认备份是好的：在副节点上开一个临时数据库，把最新一份恢复进去，数一下表里的行数，再删掉临时库。这一步不碰正式的数据库。

```bash
docker run -d --name restore-check -e POSTGRES_PASSWORD=只在这里用的临时密码 postgres:18-alpine
docker cp /var/backups/sub2api-db/<最新一份>.dump restore-check:/tmp/db.dump
docker exec restore-check sh -c 'sleep 5 && createdb -U postgres sub2api && pg_restore -U postgres -d sub2api --no-owner /tmp/db.dump'
docker exec restore-check psql -U postgres -d sub2api -c 'select count(*) from users'
docker rm -f restore-check
```

真要恢复到正式的数据库时：先停掉两台的 Sub2API，确认没有别的程序在写数据库；用和数据库同版本的 `pg_restore --clean --if-exists --no-owner`
以 Sub2API 的数据库账号恢复；再启动 Sub2API。恢复会覆盖数据库里现有的内容，备份时间之后的新数据（新的用量记录、充值）会丢，做之前先想清楚。

## 报警规则

- 一次异常不报，连续两次（约 2 分钟）才报；恢复时说一声。
- **一台的请求失败明显比另一台多**：近 5 分钟至少失败 5 个、失败率至少 20%，而且至少是另一台的两倍。两台用的是同一批上游账号，一起变差多半是上游的问题（主看板和自动换号会处理），这里不报；只有一台变差，多半是这台机器自己的问题，会响铃。哪台的数读不到，这一轮就不判断。
- 读不到（取不到）连续三次才报：指标取不到、容器状态取不到。读不到的那一轮既不算异常，也不算恢复。
- 中台连不上或数据过期时，节点和隧道的报警原地不动，不会误发「恢复」。
- **隧道断了的时候只报隧道。** 副节点连不上是同一件事，副节点的离线先不另报，等隧道恢复后仍然离线，再单独报。
- 磁盘超过 85% 报一次，降到 80% 以下才算恢复；内存超过 90% 报一次，降到 85% 以下恢复。
- 数据库备份超过 26 小时没有新的一份，报一次；备份目录连续三次读不到，另报一次。都不响铃。
- 本月流量用到额度的 80% 报一次；回到 80% 以下（进了新的计费月，或者额度调高了）说一声。数字是中转塔台自己记的，中台暂时连不上也照样判断。没设额度就不报。
- 响铃的：中台连不上、节点离线、隧道不通、Sub2API 没响应、容器不在运行、一台的请求失败明显比另一台多、指标或容器状态取不到。
  不响的：磁盘、内存快满，流量快用完，数据库备份断了，以及所有恢复消息。
- 发送失败的消息，会在下一轮重新发送。
- 报警状态只在内存里：重启后连续次数从零开始；停机期间已经恢复的项，不会补发恢复消息。

## 隧道是怎么检查的

主节点用 TCP 连一下副节点 agent 的端口（就是 `WORKER_AGENT_URL` 里的地址）：

- 连上了，或者被对面明确拒绝：说明包已经到了对面，隧道是通的。
- 超时、网络或主机不可达、本机没有 `WG_LOCAL_IP` 这个地址：隧道不通。
- 地址解析失败（多半是配置写错）：取不到。

这个检查不用 ping，不需要任何特殊权限，所以 systemd 里可以保留 `NoNewPrivileges`。

## 这一版去掉了什么

- 独立的集群页面：数据改由登录后的面板提供。
- 页面上的「最近请求」列表：对监控没有用。
- 数据库、Redis 的细节卡片：这一版没有保留，需要时再单独加回来。
- 反向代理负载均衡的「故障切换就绪」块：原来是写死的，没有真实数据来源。
- WireGuard 的「Active / 1.1ms」：取不到时也显示成正常，现在改成真实的 TCP 检查结果。
- 全链路检查里写死的「全绿测试通过 (6/6)」和一直为真的隧道检查：现在每一项都从真实数据算出来。

## 已知限制

- CPU 占用率要两次采样才有值，第一次显示「取不到」是正常的。
- 副节点挂掉由主节点发现并报警；如果主节点整机挂了，这套中台也跟着停，目前没有第三方来盯主节点。
- 报警状态只存在内存里，重启后会重新积累连续次数。
- Sub2API 健康检查地址和期望的容器名，要在配置里填对；填错了就一直显示「取不到」。
- 运行账号在 docker 组里，等于 root 权限。所以 NoNewPrivileges 能防的范围有限。要彻底解决，需要只读的 docker 代理，以后再做。
- 部署后要再看一次：健康检查请求会不会被计入请求数（现在的口径只数 `/v1/`，理论上不会）。
- 「近 5 分钟客户请求」只读 Sub2API 日志的末尾：先读 2000 行，5 分钟内的日志更多就再读 20000 行。还读不完，就显示「取不到」，不显示数不全的数字。
